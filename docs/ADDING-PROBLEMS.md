# Adding problems

Arbiter has two ways to add a problem. Use the seed folder for anything that should live in the
repository, and the admin panel for one-off problems on a running instance.

| | Seed folder (`seed/problems/<slug>/`) | Admin panel (`/admin/problems`) |
|---|---|---|
| Lives in | git, reviewed like code | the database of one instance |
| Tests | generated by `gen.py`, checked by `ref.py` | uploaded, or generated from the reference solution |
| Verified by | `scripts/verify-problems.py` (Docker, every program, time budgets) | Validate reference (the real judge) |
| Best for | a curated problem set | a quick problem for a contest |

## One problem through the seed folder

The folder protocol (files, `meta.json` fields, tag list, test counts, time budgets) is in
[seed/problems/README.md](../seed/problems/README.md). The steps:

1. Create `seed/problems/<slug>/` with `problem.md`, `meta.json`, the two samples
   (`tests/01.in`, `tests/02.in`) and their walkthroughs (`tests/01.md`, `tests/02.md`).
2. Write `ref.py`, `ref.cpp` and `gen.py`, plus `slow.py` or `wrong.py` where a naive or buggy
   solution is worth catching.
3. Generate the tests and check the sample outputs by hand:
   ```
   python scripts/gen-tests.py <slug>
   ```
4. Verify every program in Docker until the row says PASS:
   ```
   python scripts/verify-problems.py <slug>
   ```
5. Pin the generated files, then load the problem and judge it through the real API:
   ```
   cd seed/problems && sha256sum -b */tests/* > CHECKSUMS.sha256 && cd ../..
   npm run db:seed
   npm run judge:refs
   ```
   `db:seed` wipes and recreates the demo data. `judge:refs` submits every reference, slow and
   wrong program through the API and checks each verdict.
6. Commit the folder with its two samples and the updated `CHECKSUMS.sha256`. The hidden tests
   (`tests/03.*` and up) stay out of git; anyone can regenerate them byte for byte with
   `npm run problems:gen`.

## Planning a large set

Points to settle before adding hundreds of problems:

- **Original statements.** Problem ideas such as two-sum or longest increasing subsequence are
  free to use, but the statement text on LeetCode, GeeksforGeeks and similar sites is copyrighted.
  Write every statement in your own words. A `## Notes` line can name the classic problem it
  follows.
- **Input and output format.** Arbiter judges whole programs over stdin and stdout, as Codeforces
  does. LeetCode-style "complete this function" problems need a small per-language driver that
  reads the input, calls the function and prints the result. That driver does not exist yet;
  build it before writing function-style problems.
- **Tags.** `scripts/verify-problems.py` (`TAGS`) holds the allowed tags. Common DSA topics such as
  linked lists, trees, backtracking, bit manipulation and sliding window are not in it yet; add
  them there and in [seed/problems/README.md](../seed/problems/README.md). The app itself accepts
  any tag.
- **Size and seed time.** The 15 seed problems generate about 90 MB of hidden tests (about 6 MB
  each), so 500 problems at the same density would be about 3 GB. Keep large tests to the few that
  separate correct from naive solutions. Seeding re-inserts every test case, so it slows down
  with the set.
- **Batches.** Add problems in batches of 10 to 20: generate, verify and commit each batch, so a
  broken generator never blocks the rest.
